# DEKIRU Game Creator — 会員保存・短い共有URL 設計案

作成日：2026-09-29

状態：2026-09-29にユーザー承認済み。実装計画の作成段階。未実装・未契約。

## 1. 利用者にとっての完成形

一般の先生・保護者が問題を作り、短いURLを子どもに渡すと、そのまま襖ゲームで遊べるようにする。作成者は自分のゲームを保存・編集・公開停止できる。将来の有料プランに備えるが、今回は決済を実装しない。

承認済みの方針：

- 作成・プレビュー・既存のHTML書き出し・編集用ファイル保存は、登録不要で残す。
- オンライン保存とURL発行のときだけ、作成者がログインする。
- 遊ぶ子どもにはアカウントを作らせない。
- URLに問題文を埋め込まない。問題数を増やしてもURLの長さは変わらない。
- 完成した襖ゲームの画像、入力判定、動き、BGM、画面構成は変更しない。
- 既存DEKIRUシリーズの会員管理はまだないため、新しく用意する。

今回新しく提案すること：

- ログインはまずGoogleアカウントに対応する。
- 会員管理・問題保存にはSupabaseを第一候補とする。
- 下書き保存と「配布内容の更新」を分け、編集途中の内容を子どもに見せない。
- 無料試験運用の上限は、保存20件／同時公開10件／1件200問・256 KiBとする。
- 公開ゲームの一覧検索、成績収集、決済、メールログイン、共同編集は今回含めない。

この書面の承認は、有料契約・購入・本番アカウント作成の承認を兼ねない。外部設定時に所有者・サービス・費用を別途確認する。

## 2. 技術案の比較と推奨

| 案 | 利点 | 注意点 |
| --- | --- | --- |
| Supabase Auth＋データベース（推奨案） | 作成者と教材の関係、公開版、プラン別制限をまとめて管理しやすい。保存数チェックと保存を同一処理にできる | 無料版は低活動時に休止する。安定運用には運用費の検討が必要 |
| Firebase Authentication＋Firestore | Googleログインと無料枠を使って開始する候補。既存Firebase環境がある場合に合わせやすい | 保存・公開件数の同時更新や将来の決済連携には、それぞれ安全な実装・料金枠の検討が必要 |
| 匿名で公開して管理用URLを渡す | 登録の手間が少ない | 管理URL紛失、本人確認、複数端末、将来の課金との整合が難しくなるため不採用 |

比較の結論は、このアプリの保存・所有者管理・将来拡張に対する設計上の判断。特定サービスだけで課金対応が自動的に完成するわけではない。

Supabaseは認証とデータへのアクセス制御を組み合わせられる。GoogleログインにはGoogle側のOAuth設定も必要になる。[Auth](https://supabase.com/docs/guides/auth)、[Googleログイン](https://supabase.com/docs/guides/auth/social-login/auth-google)

FirebaseにもGoogleログインと無料利用枠がある。[Googleログイン](https://firebase.google.com/docs/auth/web/google-signin)、[料金](https://firebase.google.com/pricing)

## 3. URLとデータ配信

提案するURL形式（下記は説明用で、発行済みリンクではない）：

`https://ruriru-app.github.io/DEKIRU-GameCreator/p/?g=G7m2Pk8wQ4t9R3vX6nYzAa`

- 現在のドメインでは75文字。許容上限は80文字として自動検査する。
- IDは暗号学的乱数128ビットをBase64urlで表した22文字。サーバーで生成し、重複は一意制約と再試行で防ぐ。
- 問題文・題名・日本語・メールアドレス・ユーザーID・認証情報をURLに入れない。
- 外部の短縮URLサービスに依存しない。
- 同じゲームの公開内容を更新してもURLを変えない。別ゲームとして複製した場合は新しいIDを発行する。
- 公開停止中は同じURLで「このゲームは現在公開されていません」と表示する。再公開では同じURLを使う。
- 存在しないID、停止中、削除済みは同じ案内とし、所有者情報は返さない。
- 推測しにくいURLでも、知っている人は誰でも遊べる。会員限定・パスワード保護とは異なる。
- 学校のドメイン制限やClassroom側の扱いまで保証するものではない。URLを短くすることと、学校のアクセス許可は分けて確認する。

配信の流れ：

1. 作成者が確認した問題データを保存・公開する。
2. サーバーが短いIDと公開用の問題データを対応付ける。
3. 子どもがURLを開くと、共通プレイヤーがIDで公開データ1件を取得する。
4. 既存のタイピングエンジン・襖テンプレートに、そのデータを渡して起動する。

オンライン用に約40 MBの自己完結HTMLを毎回アップロードしない。画像・音声・実行コードは共通配信し、データベースに保存するのは問題と設定だけにする。ブラウザーのキャッシュを利用するが、初回には画像・音声の転送が必要。完全オフラインで遊ぶ用途には既存のHTML書き出しを残す。

## 4. 作成画面とマイゲーム

現在の色・レイアウトを維持し、次を追加する。

- ヘッダー：ログイン／アカウント表示／ログアウト／「マイゲーム」。
- 編集側：「オンライン保存」。ファイル保存とは別の保存状態を表示。
- 配布側：「共有URLを作る」、公開済みなら「配布内容を更新」、URLコピー、別タブで確認。
- マイゲーム：自分の教材の題名・更新日時・公開状態・件数。編集、URLコピー、公開停止／再公開、削除。
- 削除前には確認し、編集用ファイルの保存を案内する。取り消せない操作を黙って実行しない。

新しい教材は下書き。公開操作の前に題名・問題数と「リンクを知っている人が閲覧できる」ことを表示する。問題に氏名などの個人情報や、共有できない内容を入れないよう案内する。

オンライン保存だけでは配布中の内容を変えない。「配布内容を更新」で、検証済みの保存内容を公開版へ一括反映する。保存や公開に失敗したら、元の下書きと公開版を保持する。

公開停止・削除で止められるのは以後のオンライン取得。すでに読み込まれたゲームや、ダウンロード済みHTMLまで回収できるとは表示しない。

## 5. ログインと編集中データ

- 第一版はGoogleログイン。Googleのパスワードをアプリが収集しない。
- 要求する権限はログインに必要な最小範囲に限る。Drive・Classroomの閲覧／投稿権限は要求しない。
- メールログインは今回実装しない。追加する場合はメール送信基盤と到達性を別途設計する。
- Googleアカウントがない、または学校からログインを制限されている人も、登録不要機能は使える。
- ログイン操作前に、同じタブ専用の一時領域へ編集状態（未反映の貼り付け欄を含む）を退避する。保持は2時間。保存できなければ認証ページへ移動せず、ファイル保存を案内する。
- OAuthはPKCEを用い、戻り先を許可済みのアプリ内URLに固定する。復帰時に認証コードをURLから除く。
- ログインに失敗・キャンセルしても編集内容を復元する。復帰だけでは自動保存・自動公開しない。
- 作成者のログイン保持は同じタブのセッション保存を基本とする。ログアウト後は会員情報・一覧・認証用一時情報を消す。
- アカウント切り替え時に別ユーザーの教材として上書きしない。
- ログアウト時に現在の編集内容を残すか、ファイル保存して消すかを確認し、共有端末に教材を黙って残さない。
- 子ども用プレイヤーでは認証SDK・作成者セッションを必要としない。

実装には公式SDKを固定バージョンで取り込み、既存の単一HTML書き出しには認証SDKを混入させない。[PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow)

## 6. 保存構造と責任分離

| 要素 | 保存・担当するもの |
| --- | --- |
| 認証サービス | 作成者のログインIDと認証。子どものアカウントは作らない |
| accounts | 作成者ID、利用状態、サーバー管理のプラン参照 |
| plan_limits | 保存件数・公開件数・問題数・容量・許可テンプレート |
| games | 所有者ID、下書きデータ、更新番号、作成／更新日時 |
| publications | ゲームID、共有ID、公開スナップショット、公開状態、公開版番号 |
| 共通プレイヤー | 許可された公開データを、既存ゲームに渡す |
| クラウド接続層 | 認証、保存、一覧、公開、停止、削除。ゲーム演出から分離する |

問題データは既存の `schemaVersion: 1`、`gameType`、`templateId`、`title`、`questions`、`settings` を基準にする。所有者ID・共有ID・更新番号は外側の管理情報であり、編集用ファイルに認証情報を入れない。

公開版には、許可済みのランタイムバージョンも記録する。将来エンジンを変更するときは既存公開ゲームとの互換性を検証し、互換でない変更は別バージョンとして扱う。初版は現在の完成済みランタイムを再利用する。

実装上の境界案：

- `core/cloud/`：接続設定、認証、保存API、URL処理、クラウド用検証。
- `app/account/`：マイゲームと認証復帰画面。
- `p/`：共有プレイヤー。
- `supabase/`：DB定義・アクセス権・サーバー処理・検証。
- `Typing/creator/`：最小限のクラウド操作UIと状態連携。

`Typing/core/`、襖のrenderer・event-controller・style・manifest・画像・音声は原則変更しない。起動のためにゲーム内部変更が必要と判明した場合は、理由を提示して設計を見直す。

ファイル保存済み・クラウド保存済み・公開反映済みは別々に追跡する。通信中にユーザーが編集した場合、古いスナップショットの保存成功で新しい変更を「保存済み」にしない。

## 7. 権限・検証・同時操作

- 本文テーブルは匿名アクセス禁止。作成者は自分のゲームだけを取得・変更できる。
- RLSと明示的な権限を設定し、画面でボタンを隠すだけの制限にはしない。
- 所有者は検証したログイン情報から確定し、ブラウザーから送られた所有者IDを信用しない。
- 初回ログイン時のアカウント作成は重複しても1件となる処理にし、free以外を利用者の申告で選べない。利用停止中のアカウントについては書き込みと公開データの新規取得を拒否する。
- 所有者向け書き込みはDB関数経由とし、通常の表への直接書き込み権限を与えない。認証IDと所有者の一致を毎回検査する。
- 公開閲覧用Edge Functionは共有ID1個だけを受け取り、公開中のスナップショットだけを返す。全件一覧、作成者名、メール、下書きは返さない。
- 公開読取り用DB関数の実行はサーバー専用ロールに限定する。匿名利用者がDBを直接列挙する経路を作らない。
- 管理用秘密鍵・OAuth秘密情報はサーバーの秘密領域に限る。GitHub、ブラウザー、教材HTMLへ入れない。ブラウザー用の公開可能キーとは区別する。
- 特権DB関数は必要最小限にし、固定search_pathと限定した実行権限を使う。
- 下書きは空欄を保存できる。公開には1問以上と各問の問題・正解・よみを必須とする。
- 題名80文字、各問の問題文1000文字、正解200文字、よみ200文字、ヒント800文字、ID128文字以内。重複ID、想定外の型、未知のゲーム／テンプレートを拒否する。
- データ容量・件数・フィールド許可リスト・音量範囲をサーバーでも検証する。画像URL、音声URL、HTML、任意コードを教材として実行できないようにする。
- 文字は安全に文字列として表示し、問題に書かれたHTMLを実行しない。
- 件数制限の確認と保存／公開を作成者単位のトランザクションで行い、同時リクエストによる超過を防ぐ。
- 更新番号の一致を条件に更新する。不一致は競合表示とし、自動上書きしない。
- 新規作成には再試行用IDを持たせ、保存結果の応答だけ失われたときに教材を二重作成しない。
- 公開スナップショットの読取りはキャッシュさせず、URLを開き直した時点で公開状態を確認する。素材キャッシュとは別扱い。
- 公開プレイヤーにはnoindexとno-referrerを設定する。ただし検索除外はアクセス制限ではない。

アクセス制御と特権関数は、公式資料の権限モデルに沿って試験する。[RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)、[DB関数](https://supabase.com/docs/guides/database/functions)、[APIキー](https://supabase.com/docs/guides/getting-started/api-keys)

## 8. 初期上限と不正利用対策

試験運用の提案値。将来の料金表や永久無料枠を約束する値ではない。

| 項目 | 初期案 |
| --- | --- |
| 1アカウントのクラウド保存 | 20ゲーム |
| 同時公開 | 10ゲーム |
| 1ゲームの問題数 | 200問 |
| 1ゲームの問題データ | UTF-8で256 KiB以下 |
| 作成者の更新系操作 | 1分20回／1日500回 |
| 同一接続元の公開読取り | 1分600回を初期値とし、学校の共用回線で試験する |

サーバー側で上限を強制する。公開読取りの制御に必要な接続元は、サーバー秘密情報を用いた日替わりのハッシュ化識別子とし、24時間以内に失効・除去する。これは完全な匿名性の保証ではない。教材本文や生のIPを独自の長期ログに残さない。制限超過には待ち時間を案内し、無限再試行しない。接続元だけの判定で完全な不正対策ができるとはみなさない。

更新回数は作成者単位でDB側でも検査し、APIを直接呼んでも回避できないようにする。公開読取りの短期カウンターはサーバー専用処理で管理し、期限切れの記録を定期除去する。定期除去の設定と動作確認を外部環境構築時に含める。

学校の共用回線・一斉アクセスを想定して調整し、想定外の急増時は管理者が新規保存／新規公開を停止できる運用手順を用意する。利用量の確認と警告、バックアップ・復元・不正投稿の停止手順を公開前チェックに含める。

ローカルの編集用ファイルは現行の5 MB制限を維持する。クラウド上限を超える既存ファイルもローカルで開けるようにし、クラウド保存だけ理由付きで断る。

## 9. 将来の課金とプライバシー

今回のプランはfreeのみ。アカウントに紐づく許可機能・上限はサーバーで決め、利用者自身が有料プランへ書き換えられないようにする。

将来の有料化では決済サービスの通知をサーバーで検証してプランへ反映する。今回は決済、カード情報、料金画面、有料契約の自動更新処理を作らない。既存データを突然削除するようなプラン変更も実装しない。

一度配ったHTMLや、遊ぶために配信した画像・音声の回収／完全なコピー防止はできない。将来は主にクラウド保存枠、共有管理、追加機能などを課金対象の候補とし、既存の無料HTML配布との両立を別途決める。

- 子どもの氏名、メール、学習履歴、成績を今回の機能では収集しない。通常のホスティング／認証サービスのアクセスログまで存在しないとは説明しない。
- 作成者の認証情報と非公開下書きは、教材閲覧者に見せない。
- 共有は「リンクを知っている人向け」で、厳密な学級限定共有ではない。
- 保存先・保存する内容・削除方法・問い合わせ方法を利用者向けに説明する。
- 自分の教材の削除を用意する。アカウント削除の初期受付は認証済み利用者からの申請と管理者対応とし、公開停止→教材削除→認証情報削除の手順を文書化する。
- 不正な内容の報告・停止の連絡先、管理者の対応方法、運用バックアップの保持期間は一般公開前に所有者と確定する。これは実装の曖昧さではなく、本番運用開始の承認条件とする。

## 10. 費用と公開先

確認日：2026-09-29。料金・制限は契約前にも再確認する。

SupabaseのFreeは月額0 USDで、DB 500 MBなどの上限がある。低活動が続くと約1週間で休止対象になるため、「無料でいつでも止まらないサービス」とは案内しない。Proは月額25 USDからで、利用量・追加構成により費用が増える。[料金](https://supabase.com/pricing)、[無料プロジェクトの休止](https://supabase.com/docs/guides/platform/free-project-pausing)

提案する段階：

1. ローカル実装と無料の検証環境で動作・権限を確認する。有料契約やカード登録はしない。
2. 一般公開前に、休止リスクを許容する無料試験公開か、予算を設けた安定運用かを所有者が選ぶ。
3. 費用が発生する契約変更は別途明示的に承認を得る。「利用者に無料提供」と「運営費がかからない」は別の話として説明する。

GitHub Pagesは商用SaaSなどの用途に制限がある。将来の課金サービスの恒久的な公開基盤としては前提にしない。現行の無料版はこの作業では移転せず、商用化前に利用条件に合う公開先を選ぶ。GitHubはコード管理に引き続き使える。[GitHub Pagesの制限](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

外部環境は所有者が管理するSupabaseプロジェクトとGoogle側のOAuth設定を使う。管理者のサインインや同意が必要な場面は所有者に依頼し、秘密鍵をチャットへ貼るよう求めない。一般公開前に利用者データの保存地域と運用担当を確認する。

GitHub Pagesの同一ドメイン配下にある別プロジェクトは同じオリジンになるため、パスが違うだけで認証用のブラウザー保存領域が隔離されるとは考えない。会員機能の広い一般公開前には、専用オリジンへの移行も含めて安全性を確認する。

共有URLは公開先に結び付く。長期運用でURLを変えたくない場合、広く配る前に独自ドメインの採否を決める。今回は購入・移転しない。上記75文字のURLは現在の公開先での形式案であり、将来の移転でも永久に同じURLが使えるとは約束しない。

## 11. エラー時の振る舞い

| 状況 | 対応 |
| --- | --- |
| 設定未完了・保存サービス障害 | 既存の登録不要機能は使える。クラウド機能だけ理由を表示 |
| ログイン失敗・中断 | 編集内容を保持／復元し、再試行できる |
| 通信失敗・保存枠超過 | 内容を消さない。保存成功とは表示せず、ファイル保存を案内 |
| 同時編集で更新番号が変わった | 上書きせず、再読込みか別コピー保存を選べる |
| 公開用データが不完全 | 問題番号と項目を示す。旧公開版を維持 |
| 公開停止・削除・不正なID | 個人情報を出さず、現在遊べない旨を表示 |
| プレイヤーの通信障害 | 教材不存在と区別し、再読み込みを案内 |
| URLコピーが使えない | URLを選択して手動コピーできる |

## 12. 受け入れ条件

実装完了時に、以下を結果付きで報告する。この設計書の作成時点では新機能の検証は未実施。

1. 未ログインでも既存の作成・試遊・ファイル保存・HTML書き出しが使える。
2. 認証遷移の成功・キャンセル・保存領域エラーで編集中の内容を失わない。
3. 作成者A／作成者B／未ログインの3者で、他人の下書き・変更・削除・プラン変更を拒否する。
4. 共有IDから公開データ1件だけを取得でき、一覧や個人情報を取得できない。
5. 同時保存・二重クリック・応答喪失・同時公開でも、重複と上限超過を防ぐ。
6. 1問でも200問でも共有URLは75文字（現在の形式）で、内容や認証情報が入らない。
7. 下書き保存だけでは公開内容が変わらず、明示的な更新で同じURLに反映される。
8. 公開停止・削除後の新規取得は失敗する。素材キャッシュが残っていても本文を再取得する。
9. プレイヤーから認証や成績送信が発生しない。公開データへ任意のコード・素材URLを混入できない。
10. 既存の入力判定、IME警告、枠色、出題時の不要な揺れ、開始時の接近、襖の開閉・移動、クロスフェード、クリア表示、音声を回帰確認する。
11. 既存57件の自動テストに加え、権限・上限・公開更新のサーバーテストと公開URLのブラウザー試験を通す。既存テスト件数が変われば実数を報告する。
12. PCの別ブラウザー／未ログイン状態で公開URLを試す。タブレットは実機または同等環境で確認できた範囲だけを報告する。
13. Classroomへの貼り付けは、利用可能なアカウントと投稿先がある場合に別途確認する。未確認を確認済みとせず、試験のために勝手にクラスへ投稿しない。
14. 秘密情報が公開ファイルにないこと、利用者向け説明と削除・停止・バックアップの運用手順が用意されていることを確認する。
