## 接続開始のゲート

1. 下記のローカル／CI試験を通す。`check-cloud-release` の成功だけで本番を許可しない。
2. 所有者がGoogleの同意・認証設定を確定する。Google OAuthクライアントの作成、権限設定や秘密情報の登録は、その操作時に確認する。
3. migrationの対象が専用プロジェクトであることと差分を確認してから適用。既存DBをresetしない。現在の `supabase/config.toml` はCI内の一時DB専用であり、ホストの設定を完成させるファイルではない。
4. Google provider以外と匿名登録を無効にし、戻り先を完全一致で設定する。Google側の承認済みリダイレクトURIはSupabaseの `https://xrqgsujvduyxtrbegzri.supabase.co/auth/v1/callback`。アプリへの戻り先は別で、`https://ruriru-app.github.io/DEKIRU-GameCreator/app/account/callback.html`。ワイルドカードや任意のreturnToを許可しない。[Google接続の公式手順](https://supabase.com/docs/guides/auth/social-login/auth-google)
5. 権限は `openid email profile` のみ。PKCEと同じタブの保存領域を使用。Googleの「テスト中」は、基本プロフィールだけのログインではテストユーザー限定を保証しない。「所有者だけの試験」とする場合は、認証側で登録者を制限する方法を別途確認し、未確認のままインターネットへ有効化しない。[Googleの対象設定](https://support.google.com/cloud/answer/15549945?hl=en)
6. 匿名閲覧用Edge Functionの起動部分、秘密管理、信頼できる接続元アドレス、下記の短期記録削除ジョブを設定・実測する。この入口は未完成。任意の `X-Forwarded-For` や `X-Real-IP` をそのまま信用して公開しない。
7. 正式な公開URL・公開可能キーだけを設定へ反映。`sb_secret_…`、service_role JWT、OAuth client secret、DB password、HMAC secretはホストの秘密管理に限る。GitHub、チャット、画面キャプチャ、ブラウザー用JSへ記載しない。
8. 所有者A／別の承認済み検証者B／未ログインの3者で実環境試験を行う。別アカウントを勝手に作らない。共有URLの発行・別ブラウザーの再生・更新・停止・削除を実測する。
9. 広い一般公開前に、問い合わせ先、削除・報告窓口、バックアップ保持期間、専用オリジンの採否を所有者が確定する。現在は本人利用の準備段階。Google用の連絡先承認を、Webページへのメールアドレス公開の承認とみなさない。

## 検証コマンド

```sh
pnpm install --frozen-lockfile --ignore-scripts
node tools/build-cloud-sdk.mjs
node --test tests/*.test.mjs
node tools/check-cloud-release.mjs
```

公開チェックは読取り専用。未設定の現在は失敗するのが正常。エラーコードは、未設定、無効な公開設定、80文字超のURL、管理キーらしい内容、私的ファイル、襖素材の差分、必要ファイル欠落、問い合わせ先未設定などを区別する。検出した秘密そのものを出力しない。

スキャン対象はリポジトリ直下のファイル（`.git` を除く）、`app/`, `core/`, `Typing/`, `p/`, `vendor/`, 存在する場合は `dist/` の配布物。テストには故意の偽キーがあるためスキャン対象外。秘密情報の検出は補助であり、push前にはGit差分も点検する。`.gitignore` は、すでに追跡された秘密を取り除かない。

DBはGitHub Actionsの一時的なローカルSupabaseだけで `supabase test db` と `node --test tests/integration/cloud-db.test.mjs` を実行する。本番キーや実在するメールアドレスは渡さない。実行後に一時サービスを破棄する。

ブラウザー試験：`cloud-browser-tests.html`、`cloud-account-browser-tests.html`、`shared-player-browser-tests.html`、既存の `project-file-browser-tests.html`、`input-browser-tests.html`、`feedback-browser-tests.html` など。これらのクラウド画面試験は疑似通信を使い、本物のOAuth／ホストの権限確認とは別。

## 利用者の操作

- 登録不要の編集・プレビュー・編集ファイル保存・単一HTML書き出しは端末内処理。オンライン保存は明示操作時に送信する。
- 保存20件／公開10件／1教材200問・256 KiBが無料試験のサーバー側上限。ローカル編集ファイルの既存5 MB上限とは別。
- 保存と公開を区別する。下書き保存では配布内容は更新しない。公開／更新の確認後に反映する。
- 通信結果が不明な場合は「通信を再確認」で同じ操作IDを再利用する。確認が終わるまで二重操作をしない。競合時は上書きせず、手元をファイル保存してから再読込みまたは別コピーにする。
- 共有URLは現在の公開先で75文字。リンクを知る人向けで、秘密の正解を隠す仕組みではない。問題や正解、個人情報をURL自体には含めない。
- 公開停止・削除で回収できるのは以後のオンライン取得だけ。起動済みゲームや保存済みHTMLは回収できない。

## アカウント削除・不適切な教材の停止

未確定：窓口と保持期間は一般公開前に所有者が決める。以下を担当管理者が承認後に実施する。公開フォームやメールにパスワード・トークンを送らせない。

1. ログイン済みの本人からの申請を受け、認証情報で本人と対象のUUIDを照合する。申告されたメールアドレスだけで別の利用者のデータを消さない。
2. 対象ユーザーの `private.accounts.status` を `disabled` にして、その所有者の公開版の新規取得と書込みを止める。対象を1人に限定し、事前に件数を確認する。
3. 対象の公開版・教材・冪等性記録を確認して削除する。`private.games` の削除は関連 `private.publications` に連鎖する。教材を手元に残したい本人には、停止前に編集用ファイル保存を案内する。
4. SupabaseのAuth管理画面で、照合した本人の認証ユーザーを削除する。`auth.users` → `private.accounts` →教材等は外部キーの連鎖削除。SQLでAuth内部表を直接編集しない。
5. 同一UUIDがないこと、新規公開取得が共通の404であることを確認し、本文や秘密を含めない最小限の対応記録を残す。再登録しても旧教材が復活しないことを確認する。
6. 運用バックアップからの期限到来削除と、復元時の削除済み教材の再公開防止も確認する。通常のサービス側アクセスログまで即時消えると約束しない。

不適切な教材の報告は公開URLと理由だけを受け、管理者が確認する。該当 `share_id` を対象に停止し、必要なら所有者を一時停止。報告だけで他人の全教材を自動削除しない。対応前後に対象1件を照合し、公開版のversionとゲームのversionも更新して古い編集操作と競合させる。詳細な対象付き変更は承認後に用意する。

## 保存・公開の一時停止

DB管理者だけが `private.service_control` の単一行を変更できる。操作前に対象プロジェクトと現在値を確認し、変更後は別ブラウザーで効果を確認する。

| 列 | falseのとき |
| --- | --- |
| `save_enabled` | 新規保存と既存下書きの更新を停止。読出しや削除は妨げない |
| `publish_enabled` | 新規公開・配布内容更新・再公開を停止。公開停止や削除は妨げない |
| `public_read_enabled` | 公開データの新規取得を停止 |

利用量急増時は、まず原因と無料枠の残量を確認し、必要な列だけ停止する。費用を増やして復旧させない。通常運用へ戻す前に負荷・所有者権限・600回/分境界を確認する。`enabled:false` の静的ページ変更だけでは、すでに配信したAPIへのアクセスを止められない。

## 期限切れ記録の除去

DB関数 `private.purge_expired_cloud_records()` は、期限到来した操作ID記録と、作成から23時間以上経過した公開読取りカウンターを削除する。現時点ではホスト未設定。公開読取りカウンターは日付入りHMACで、生のIPを保存しない。

所有者の承認後、専用プロジェクトでSupabase Cronを有効化し、1時間に1回、管理者権限でこの関数だけを実行するジョブを1つ登録する。重複を作らずジョブ名を固定する。本文・IP・認証情報をジョブ引数やログに入れない。CronはDB関数を直接実行し、実行状態を確認できる。[公式Cron案内](https://supabase.com/docs/guides/cron)

確認項目：手動1回と次回定期実行の成功、`cron.job_run_details` の時刻、24時間を超えた `private.read_limits.created_at` が0件、期限切れrequestsが0件。ジョブ失敗・停止中は24時間以内の実削除を保証できないため、新規公開読取りを停止し、削除処理と原因調査を優先する。復旧・休止解除時も新規公開読取りの再開前に除去する。ジョブ監視自体は未設定で、未確認のまま保持期限を達成済みとしない。

## 無料環境の休止・バックアップ・復元

Freeは低活動が続くと休止する場合がある。所有者が専用プロジェクトを確認し、DashboardのResumeを選んで復帰状態を確認する。有料アップグレードを復帰の既定手順にしない。復帰後は除去ジョブ、Auth、保存、公開・停止を再試験する。[公式の休止・復帰手順](https://supabase.com/docs/guides/platform/free-project-pausing)

無料枠に、有料プランの日次バックアップやPITRが付くとは扱わない。公式はFreeに定期的なCLIによるエクスポートと外部保管を勧めている。[公式バックアップ案内](https://supabase.com/docs/guides/platform/backups)

- **現在未設定**：保管場所、暗号化、実施頻度、保持期間、担当者、復元時の削除依頼反映。一般公開前に所有者の承認が必要。
- その間、本人の教材は `.dekiru.json` でも保存する。これはサーバー認証・公開IDの完全バックアップではない。
- 管理者バックアップは権限制限・暗号化した非公開保管先へ。GitHub、配信ディレクトリ、共有ドライブの公開領域へ置かない。バックアップ本文や接続文字列をログへ出さない。
- DB、Auth、ホストの設定・秘密情報は別々の復旧対象。Supabase CLIの通常dumpだけでAuthや全設定が復元されると仮定しない。必要な対象は公式手順に沿って確認する。
- 復元は承認済みの隔離検証先で先に試し、データ件数・所有権・RLS・関数権限・削除済み情報の再混入防止を確認する。運用DBへ上書き復元する前に、影響範囲と停止時間について別途承認を得る。
- 復元後も公開読取りを停止した状態で確認し、公開停止・削除済みの教材が勝手に復活しないことを確認してから再開する。

## 差し戻しと一般公開

接続開始に問題があれば、サーバーの必要な操作を停止し、ブラウザー側を `enabled:false` に戻して既存の登録不要機能を維持する。DBを消したり旧migrationへ破壊的に巻き戻したりしない。認証情報漏えいが疑われた場合は対象を特定し、所有者が該当する秘密の失効・再発行を行う。

一般公開の承認前に、別のDEKIRUプロジェクトと同一オリジンの保存領域を共有する点を確認する。パスやstorageKeyの違いだけでは別アプリからのアクセスを隔離できない。専用オリジン・独自ドメインを採用するかは所有者判断であり、勝手に購入・移転しない。

承認後も、公開するブランチと差分を確定→実際のPages反映を待つ→実URLのログイン／保存／共有を再試験する。「テスト画面で動く」と「配布できる」を別々に報告する。
